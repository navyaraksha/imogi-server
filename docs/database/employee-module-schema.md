# Employee module PostgreSQL schema

Migration: [`000001_employee_module.sql`](../../db/migrations/000001_employee_module.sql)

> This migration is the original V0 employee schema. The approved
> multi-tenant organization contract now requires a follow-up migration that
> adds tenant/company ownership and company-scoped employee uniqueness. Do not
> edit this already-created migration; introduce the ownership changes in a
> new migration after the organization API is approved.

## Logical model

```text
employee.employees
        1 ──────── * employee.employments
                         1 ──────── * employee.employee_assignments

employee.employees
        1 ──────── * tax.employee_tax_profiles
```

An employee is the person identity. An employment is one continuous
relationship with a company. Assignments and tax profiles are effective-dated
histories and are never replaced by editing the current employee row.

## Shared persistence decisions

- IDs use the `platform.uuid_v7` domain. UUIDs are generated by the
  application; PostgreSQL validates UUID version 7 and the RFC variant.
- `end_date` and `effective_to` are inclusive dates. A new assignment or tax
  profile closes the previous open record at `new effective_from - 1 day`.
- Sensitive NIK and NPWP values are stored as application-encrypted
  ciphertext. NIK uniqueness uses a stable application-keyed SHA-256/HMAC
  lookup value, not plaintext or an unkeyed hash.
- No table has a soft-delete column. Financially or legally relevant history
  is protected by delete-blocking triggers and restrictive foreign keys.
- `company_id` and organization-unit IDs use UUIDv7 but have no foreign key in
  this migration because the organization module's reference tables are not
  part of the approved employee migration. Those FKs should be added in the
  organization migration.

## `employee.employees`

Purpose: stores the person identity and mutable personal data exposed by the
employee API.

- Primary key: `id platform.uuid_v7`.
- Foreign keys: none; this is the root employee entity.
- Required columns: `id`, `employee_number`, encrypted NIK, NIK lookup hash,
  `full_name`, `created_at`, and `updated_at`.
- Nullable columns: `birth_place`, `birth_date`, `gender`, `email`, `phone`,
  and `address`.
- Unique constraints/indexes: `employee_number` and `nik_lookup_hash` are
  unique under the V0 tenant-wide identity assumptions.
- Checks: non-blank employee number/name, non-empty ciphertext, 32-byte
  lookup hash, and the approved gender enum.
- Indexes: unique employee number, unique NIK lookup hash, and trigram indexes
  for case-insensitive/contains search over employee number and full name.
- Historical behavior: personal fields may be updated. Employee number and
  NIK identity lookup hash are immutable. NIK ciphertext may be re-encrypted
  during key rotation without changing the identity. Hard delete is blocked.

## `employee.employments`

Purpose: stores each continuous employment relationship, including ended
relationships. A rejoin inserts a new row.

- Primary key: `id platform.uuid_v7`.
- Foreign keys: `employee_id` references `employee.employees(id)` with
  `ON DELETE RESTRICT`.
- Required columns: `employee_id`, `company_id`, `employment_type`,
  `join_date`, `created_at`, and `updated_at`.
- Nullable columns: `end_date` and `termination_reason`. They must both be
  null for an open employment, and both be populated when an employment ends.
- Unique constraints/indexes: a partial unique index permits at most one open
  employment per employee. The employee-history and company-history indexes
  support API history and company-scoped access.
- Checks: approved employment type, end date not before join date, and
  termination-reason consistency. An exclusion constraint prevents
  overlapping employment periods for the same employee.
- Historical behavior: employee/company/type/join data cannot change. An open
  employment may transition once to an ended employment. Once `end_date` is
  set, the row cannot be edited or deleted. A rejoin creates a new row with a
  new ID and leaves the old row unchanged.

## `employee.employee_assignments`

Purpose: stores historical location, department, position, and group placement
within one employment.

- Primary key: `id platform.uuid_v7`.
- Foreign keys: `employment_id` references
  `employee.employments(id)` with `ON DELETE RESTRICT`.
- Required columns: `employment_id`, `effective_from`, `created_at`, and
  `updated_at`. At least one organization-unit ID is required by a check.
- Nullable columns: `location_id`, `department_id`, `position_id`, `group_id`,
  and `effective_to`.
- Unique constraints/indexes: one partial unique open assignment per
  employment; history index by employment and descending effective date.
- Checks: at least one placement reference, valid date order, and bounded date
  range. A GiST exclusion constraint prevents overlapping periods within one
  employment.
- Historical behavior: placement fields and `effective_from` are immutable.
  The only permitted update is closing an open assignment by setting
  `effective_to`. Deletes are blocked. Creating a later assignment is the
  normal way to represent a placement change.

Assignment periods are checked by deferred constraint triggers against the
employment dates. This permits resignation to close the assignment and end
the employment in one transaction while validating the final state at commit.

## `tax.employee_tax_profiles`

Purpose: stores the tax profile snapshot applicable to each historical period,
including PTKP, tax method, and encrypted tax identifiers.

- Primary key: `id platform.uuid_v7`.
- Foreign keys: `employee_id` references
  `employee.employees(id)` with `ON DELETE RESTRICT`.
- Required columns: `employee_id`, encrypted NIK snapshot, `ptkp_code`,
  `tax_method`, `effective_from`, `created_at`, and `updated_at`.
- Nullable columns: encrypted NPWP and `effective_to`.
- Unique constraints/indexes: unique `(employee_id, effective_from)` and a
  history index by employee and descending effective date.
- Checks: non-empty encrypted values, non-blank PTKP/tax-method codes, valid
  date order, and bounded date range. A GiST exclusion constraint prevents
  overlapping profile periods for one employee.
- Historical behavior: all tax identifiers, PTKP, tax method, and start date
  are immutable snapshots. The only permitted update is closing an open
  profile. Deletes are blocked. A new tax profile version closes the prior
  version and inserts a new row.

## Resignation transaction

The application transaction should:

1. Lock and validate the open employment.
2. Close the open assignment at `last_working_date`.
3. Set employment `end_date` and `termination_reason`.
4. Perform later final-tax/document workflows in the same business boundary
   where required.
5. Commit once all deferred historical-period checks pass.

## Rejoin transaction

The application validates that the previous employment is ended, then inserts
a new employment row. It never clears `end_date` on the previous row. The
partial unique index and employment-period exclusion constraint protect the
no-concurrent-employment V0 rule.
